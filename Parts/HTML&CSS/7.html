Q61 — What is the difference between <form> and <fieldset>? Easy → Medium

✅ Ideal answer <form> represents a complete form that contains controls and can be submitted.

<fieldset> is used to group related form controls together semantically.
🔁 Follow-up: What is the purpose of <legend>? <legend> provides a caption or accessible name for the <fieldset>.
🔁 Follow-up: What is the difference between action and method? action
→ where the form data is sent
method
→ how the data is sent

For example:
<form action="/users" method="post">
🔁 Follow-up: What is the difference between <fieldset> and <legend>? <fieldset> groups related form controls.
<legend> provides a caption/name for that group.

Example:
<fieldset>
  <legend>Account Type</legend>

  <label>
    <input type="radio" name="type" value="employee">
    Employee
  </label>

  <label>
    <input type="radio" name="type" value="recruiter">
    Recruiter
  </label>
</fieldset>

This is particularly useful for accessibility because assistive technologies can understand that the controls belong to the same conceptual group.

🔁 Follow-up: Would you use a <div> instead?
If I need an actual semantic form grouping, <fieldset> is preferable because it communicates the relationship.

Q62 — What is the difference between client-side and server-side validation? Medium

✅ Ideal answer Client-side validation happens in the browser before the request is sent to the server. It provides fast feedback and improves user experience.

Server-side validation happens on the backend and is essential because the client cannot be trusted.
🔁 Follow-up: Why can't we rely only on Angular validation? Because a user can bypass the Angular application entirely and send requests directly to the API using tools such as Postman or custom scripts.

Q63 — What is the difference between <input type="submit"> and <button type="submit">? Easy → Medium

✅ Ideal answer Both can submit a form when they're associated with a form.

<input type="submit"> is an input control whose displayed content is controlled through its value.

<button type="submit"> is a button element whose content can contain text and, depending on the allowed content, richer markup.
🔁 Follow-up: What is the default type of a <button> inside a form? The default behavior is submit, so it's good practice to explicitly specify the type.

</button>

Q65 — What happens when an HTML form is submitted? Medium

✅ Ideal answer When a form is submitted, the browser identifies the successful form controls, constructs the form data, and depending on the form's method and action, sends a request to the specified URL.
🔁 Follow-up: What happens to disabled form controls during native submission? Disabled controls are generally not included in the submitted form data.

</form>

Q66 — What are "successful controls" in HTML forms? Hard

✅ Ideal answer Successful controls are form controls whose names and values are included when the browser constructs the form data for submission.

For example, a disabled input is generally not successful and won't be included. Checkboxes that are not checked are also generally not included. Controls typically need an appropriate name to contribute a name-value pair.
🔁 Follow-up: If I have an unchecked checkbox (active=true), will it be submitted? No. An unchecked checkbox is generally not included in native form submission at all. If the backend needs an explicit false, the application needs to handle that appropriately.

💻 Code

<input type="checkbox" name="active" value="true">
<!-- If unchecked, this is NOT submitted. -->

Q67 — What is the action attribute of a <form>? Easy → Medium

✅ Ideal answer The action attribute specifies the URL where the form submission should be sent.

For example: <form action="/api/users" method="POST">
The browser submits the form to /api/users.
🔁 Follow-up: What happens if action isn't specified? The form submits to the current document's URL by default.

Q68 — What is the difference between "safe" and "idempotent" HTTP methods? Medium

✅ Ideal answer Safe methods do not modify server state — they only retrieve data. Examples: GET, HEAD, OPTIONS.

Idempotent methods produce the same result whether the request is made once or repeated multiple times. Examples: GET, HEAD, OPTIONS, PUT, DELETE.

POST is neither safe nor idempotent.
Every safe method is also idempotent, but not every idempotent method is safe (e.g. DELETE changes state but repeating it yields the same outcome).
🔁 Follow-up: Is POST idempotent? No. Calling POST twice usually creates two resources (e.g. two orders). That's why browsers warn you when refreshing a page after a POST submission.
🔁 Follow-up: Is DELETE idempotent even though it changes state? Yes. Deleting the same resource twice leaves the server in the same state as deleting it once. Idempotency is about the final state, not about whether the method changes data.
🔁 Follow-up: Is PATCH idempotent? Not necessarily. PATCH applies a partial modification, and some patches (e.g. "increment counter by 1") are not idempotent.

💻 Code

requests.http — Visual Studio Code
requests.http
# ✅ Safe + Idempotent

# ✅ Idempotent, NOT safe

# ❌ NOT safe, NOT idempotent
POST   /users          → 201 Created     (each call creates a NEW user!)

Q69 — What is HTML escaping and why is it important? Medium → Hard

✅ Ideal answer HTML escaping converts special characters into safe HTML representations so that user-provided text isn't interpreted as HTML markup.

For example: < becomes &lt;, > becomes &gt;, and & becomes &amp;.

This is important when displaying untrusted content because it can help prevent HTML injection and XSS vulnerabilities.
🔁 Follow-up: Is escaping alone enough to prevent all XSS? No. XSS prevention depends on the context and proper output encoding, safe APIs, sanitization where appropriate, and framework protections. Different contexts such as HTML, JavaScript, CSS, and URLs require different handling.
🔁 Follow-up: What is the difference between escaping and sanitization? They solve different problems and are often used together:

Escaping (Encoding)
→ Converts special characters into their safe representation so they display as text, not as code.
→ Applied at output time, right before rendering.
→ Reversible (you can decode it back), and it does not remove anything — the original characters are still there, just shown safely.
→ Example: <script> → &lt;script&gt;

Sanitization (Filtering)
→ Parses the input and removes or rewrites dangerous parts (e.g. strips <script> tags, event handlers like onclick, or javascript: URLs).
→ Usually applied before storing or before displaying rich HTML the user is allowed to submit.
→ Not reversible — the dangerous parts are gone.
→ Libraries: DOMPurify, sanitize-html, bleach (Python).

Rule of thumb:
<span>  — you have plain text → escape it (textContent).
<div>  — you must render rich HTML → sanitize it first, then insert with innerHTML (or better, use a trusted library).

⚠️ Never rely on escaping alone when the output context is not HTML text (URLs, JS strings, CSS).

💻 Code

index.html — Visual Studio Code
index.html
<!-- User input: <script>alert(1)</script> -->

<!-- ❌ Unsafe: Renders as HTML -->
<div><script>alert(1)</script></div>

<!-- ✅ Safe: Escaped -->
<div>&lt;script&gt;alert(1)&lt;/script&gt;</div>

<!-- ✅ Safe: Sanitized (DOMPurify) -->
<div id="output"></div>
<script>
  const dirty = "<b>Hello</b><script>alert(1)</script>";
  document.getElementById("output").innerHTML = DOMPurify.sanitize(dirty);
  // Result: <b>Hello</b>  (script removed)
</script>

Q70 — What is XSS, and how does it differ from CSRF? Hard

✅ Ideal answer XSS (Cross-Site Scripting)
A vulnerability where an attacker manages to run malicious JavaScript in another user's browser, in the context of a trusted website.
Example: if an app unsafely renders user-controlled HTML, an attacker can inject a script that runs when another user views the content.
Types: Stored, Reflected, and DOM-based XSS.

CSRF (Cross-Site Request Forgery)
An attack where a malicious website tricks the user's browser into sending an authenticated request to a trusted site where the user is already logged in — without the user's knowledge.
The attacker doesn't steal the cookie; they exploit the fact that the browser automatically attaches cookies to every request to that origin.
🔁 Follow-up: Does Angular protect against XSS? Angular provides built-in protections by escaping/interpreting template-bound values safely and sanitizing certain potentially dangerous values and contexts. However, developers can still introduce vulnerabilities by bypassing Angular's security mechanisms.
🔁 Follow-up: What is the danger of using innerHTML with user input? If untrusted input is inserted as HTML without proper sanitization, an attacker may inject malicious markup or scripts, creating an XSS vulnerability.
🔁 Follow-up: How do XSS and CSRF differ, and how do we prevent each? They are completely different attacks — they break different trust assumptions and require different defenses.

XSS breaks trust in the website's content.
The attacker gets code execution in the victim's browser, in the target site's origin.
→ Defense: textContent, output encoding, sanitization (DOMPurify), CSP, HttpOnly cookies.

CSRF breaks trust in the user's browser identity.
The attacker gets no code execution — they only cause the browser to send a request the user didn't intend.
→ Defense: CSRF tokens, SameSite cookies, Origin / Referer checks.

Critical interaction: if XSS exists, CSRF protection is defeated — the injected script can read the CSRF token from the page and forge valid requests. That's why fixing XSS is a prerequisite for CSRF protection to be meaningful.
🔁 Follow-up: How does a CSRF token actually work? 1. When the user loads a form, the server generates a random, unpredictable token and stores it in the user's session.
2. The server embeds the same token in a hidden input inside the form: <input type="hidden" name="csrf_token" value="abc123...">
3. On submit, the server checks that the token in the request matches the token stored in the session.
4. A malicious site cannot read the token (Same-Origin Policy), so it cannot forge a valid request.

⚠️ The token must be tied to the user's session and must not be readable by an attacker — that's why cookies should be HttpOnly and SameSite=Lax/Strict.

💻 Code

app.js — Visual Studio Code
app.js
// ===================== XSS =====================
// ❌ DANGEROUS: XSS Vulnerability
const userInput = "<img src=x onerror=alert('XSS!')>";
document.getElementById('output').innerHTML = userInput;

// ✅ SAFE: Uses textContent (escapes HTML)
document.getElementById('output').textContent = userInput;


// ===================== CSRF =====================
// ❌ DANGEROUS: No CSRF token — a malicious site can auto-submit this
// <form action="https://bank.com/transfer" method="POST">
//   <input name="to" value="attacker">
//   <input name="amount" value="1000">
// </form>
// The victim's cookie is sent automatically → transfer happens!

// ✅ SAFE: Every state-changing form must include a CSRF token
// <form action="/transfer" method="POST">
//   <input type="hidden" name="csrf_token" value="RANDOM_TOKEN">
//   ...
// </form>
// Server checks: does this token match the one stored in the user's session?
